## Behavior

- Migration `0006_events_consumer_state` (owner `events`): `events.consumer_processed` (organization, consumer, event ID) and `events.consumer_position` (organization, consumer, ordering key → last applied version), both with forced tenant RLS. The runtime role may SELECT/INSERT, and UPDATE only `position`/`updated_at`.
- `consumeEvent(db, consumer, envelope, handler)` runs in one tenant transaction:
  1. record the event as processed (a redelivery returns DUPLICATE without running the handler);
  2. for PER_AGGREGATE events, lock the consumer's position: an already-applied version is DUPLICATE, a jump ahead throws `OrderingGapError` (the whole transaction rolls back, so the queue redelivers later), the next version runs the handler and advances the position;
  3. NONE and PER_BRANCH events are deduplicated by event ID only (the envelope has no branch sequence; branch ordering stays with the Edge → Cloud inbox sequence).
- `startEventConsumer` runs a BullMQ worker on `rifad-cloud-events`, fans each validated envelope out to its registered consumers, records a CONSUMER span per delivery, and fails the job on handler errors or gaps so BullMQ retry/backoff applies. Events without consumers are acknowledged; duplicate consumer names are rejected.

## Risk review

Abuse/failure cases: duplicate delivery after the 24 h job dedupe window (processed table), out-of-order delivery (position + gap error), partial effect (single transaction), cross-tenant state (forced RLS keyed by the envelope's organization), poisoned job data (envelope validation before any write). Residual: a permanent gap exhausts BullMQ attempts and leaves a failed job; there is no operator tooling or alerting for it yet. Processed rows grow without retention (G02). Performance: one extra insert and, for ordered events, one locked read and upsert per delivery; not measured.
