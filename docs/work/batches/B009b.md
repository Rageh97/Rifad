## Behavior

- `ordering-application`: synchronous commands (open, add item, change quantity, remove, submit round, void, cancel, begin/abandon closing, close with receipt). Every command reads, changes and saves the check and appends its events through ports inside one unit of work. `addItem` resolves the price through `PricingPort` before the transaction and freezes the snapshot on the line.
- `ordering-edge` (`runtime:edge`):
  - Edge migration `0101_ordering_check` stores each check as a versioned document with status. Rounds and voided lines stay inside it as history.
  - Updates use optimistic versions (`CONCURRENT_MODIFICATION`). Reads and writes are limited to the device's tenant and branch.
  - Events become EDGE-plane, PER_AGGREGATE envelopes (aggregate type `check`, the aggregate version, the request's correlation ID, idempotency key `<type>:<check>:<version>`) appended to the local outbox.
  - Each command runs in one immediate SQLite transaction, so the check and its outbox events commit together without internet.
- Edge store fix, found while building this (B007e had not shipped):
  - Per §33, EDGE-plane events are dispatched locally **and** synced to the Cloud, so `pendingCloudSync` / `markSyncedThrough` now cover both planes and local dispatch only EDGE.
  - `openEdgeStore({ migrations })` applies context-owned Edge migrations after the store's own.

## Risk review

Abuse cases: a check for another tenant or branch (scope check on every read and write), lost round or event on crash or power loss (single transaction, WAL plus full sync), concurrent edits from two tablets (version conflict), price changes after sending (frozen snapshot). Residual: Edge API authentication (PIN/session, device trust) is not decided; who may approve voids and cancellations is enforced by the future Edge permission check; the document storage is fine for a single-writer Edge but Cloud projections will need relational read models (sync, M0-044).
