## Behavior

- `listFailed(db, limit)` returns the oldest FAILED rows (event ID, tenant, event type, aggregate type, attempts, last error, recorded time); payloads are never returned.
- `retryFailed(db, selection)` returns rows to PENDING with attempts reset and `available_at = now()`, so the relay republishes them; `jobId = eventId` keeps that idempotent. Explicit event IDs (1–1000 UUIDs) may include any failure; `allQueueFailures` selects only `QUEUE_UNAVAILABLE` rows, because `INVALID_ENVELOPE` rows would fail again and need a per-event decision.
- `pnpm outbox:failed list [--limit N]` and `pnpm outbox:failed retry --event-id <uuid>… | --all-queue-failures` run as the scoped relay role through a loopback-only `RIFAD_RELAY_DATABASE_URL`, after `pnpm build`, and print one JSON line.
- No migration: the relay role already holds SELECT and the needed column UPDATE grants (0003).

## Risk review

Abuse cases: mass replay (explicit IDs or queue-failure-only bulk, idempotent publish), poisoned events re-entering the queue (excluded from bulk), payload exposure in operator output (never printed), use against a remote/production database (loopback-only URL). Residual: retries are not yet recorded in the audit trail (M0-017 is blocked); no alerting on FAILED rows.
