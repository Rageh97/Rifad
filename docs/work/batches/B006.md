## Ownership and runtime

`@rifad/queue` and `@rifad/outbox-relay` are `layer:infrastructure runtime:cloud`; Edge cannot import BullMQ/Redis (existing rule). The relay runs in the worker only. Migration owners: `events` (0003, relay access) and `sync` (0004, inbox). `@rifad/test-containers` (`layer:testing runtime:ci`) holds the PostgreSQL/Redis harnesses and local role provisioning; production libraries do not depend on it (architecture test).

## Behavior

- Relay: claims due PENDING rows with `FOR UPDATE SKIP LOCKED` and publishes to queue `rifad-cloud-events` with `jobId = eventId`. It marks rows PUBLISHED in the same transaction.
- A crash after publishing but before commit leaves rows PENDING; the retry reuses the jobId, which BullMQ deduplicates. Completed jobs are kept 24 h as the dedupe window.
- When the queue is down, the relay records `QUEUE_UNAVAILABLE`, applies exponential backoff and stops the pass. After `maxAttempts` (default 10) the row becomes FAILED for operator action. Invalid envelopes become FAILED `INVALID_ENVELOPE`.
- The relay role `rifad_relay` (§14.1 scoped service role) can SELECT the outbox and UPDATE only status, attempts, available_at, published_at and last_error, through `TO rifad_relay` policies. It cannot INSERT, DELETE, change payload or tenant, or read any other table.
- The RLS audit now rejects any `USING/WITH CHECK (true)` policy that is not limited to an approved service role and table.
- Queue: queue Redis must report `maxmemory-policy noeviction`, otherwise readiness is `misconfigured`. Reconnects retry every 0.2–2 s; BullMQ's default backs off to 20 s.
- Worker: readiness checks `database` and `queue`. The relay starts only when `RIFAD_RELAY_DATABASE_URL` and `RIFAD_QUEUE_REDIS_URL` are both set. Logs carry counts and error codes only. Shutdown waits at most 5 s for the queue.
- Inbox: `receiveOperation` inserts `(organization, operation)` once and applies the projection effect in the same tenant transaction.
  - Redelivery with identical content (canonical JSON hash) returns DUPLICATE.
  - The same ID with different content returns `INBOX_OPERATION_CONFLICT`; a different operation at a used source sequence returns `INBOX_SEQUENCE_CONFLICT`.
  - A failed effect rolls back the inbox row, so redelivery still applies it.
  - `sequenceGaps` reports missing ranges per Edge source. Only a payload hash is stored.
- Ordering guard: APPLY at the next position, DUPLICATE at or below it, GAP beyond it. A GAP is not applied and is reported. Keys are per aggregate or per branch, and NONE events dedupe by event ID.

## Risk review

| Abuse case | Control and test |
| --- | --- |
| Relay as a cross-tenant bypass | Column grants plus role-scoped policies; denied INSERT/DELETE/payload/tenant edits and other tables; audit flags unscoped all-rows policies |
| Lost events (crash, Redis outage or restart) | Postgres is the truth; crash, outage and restart tests; append-only Redis keeps published jobs |
| Duplicate delivery | jobId dedupe; concurrent relays with SKIP LOCKED claim each row once |
| Evicting Redis | Readiness `misconfigured` test |
| Replay with altered content | Hash conflict |
| Sequence collision | Unique constraint |
| Silent loss of Edge operations | Gap report |
| Credentials in logs | End-to-end worker run checks no database or Redis password is logged |

Residual risks:
- Consumers of the queue are not implemented yet. Any consumer must use the ordering guard and its own idempotency, because jobs can repeat after the 24 h dedupe window.
- Redis persistence and `noeviction` in production are an operator responsibility (G16).
- FAILED rows have no operator tooling yet.

Performance: batch 50, poll 500 ms, an immediate next pass after a full batch, a 5 s publish timeout, and DB locks held only for the batch. These are bounds, not SLOs (G02).

## Implementation choices

- BullMQ 6 accepts `ioredis` as an optional peer; `ioredis` 6.0.0 is pinned explicitly. The optional native accelerator `msgpackr-extract` is denied a build script (pure-JS fallback), so no third-party install script runs.
- `appendToOutbox`, the inbox and the relay use parameterized SQL, so Kysely's invariant schema generics do not constrain callers.
- Test harnesses moved from `@rifad/database` into `@rifad/test-containers`, so database and relay suites share them without private imports or dependency cycles.
- Integration specs fork apps with an empty `execArgv` and no `NODE_TEST*` variables, so the app starts as in production.
